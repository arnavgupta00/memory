# Architecture 0003.2 — Hybrid Graph Reader Repair

## Decision

Architecture 0003.2 keeps the TypeScript LangGraph Contexto/Shino construction workflow from
Architecture 0003, but no longer treats the generated graph as the only readable memory. The
canonical graph remains useful structured memory; a deterministic lexical index over complete raw
sessions is the lossless safety plane.

The change repairs three independently measurable stages:

```text
memory construction → deterministic retrieval → evidence reading → compact final answer
```

Contexto and Shino remain query-blind. Only retrieval, Reader, and Answer receive the benchmark
question.

## Cadence and model calls

For `N` sessions:

```text
Contexto calls = floor(N / B)
Shino calls    = floor(N / C)
Reader calls   = 1
Answer calls   = 1

Total agent LLM calls = floor(N / B) + floor(N / C) + 2
```

The controlled repair configuration is B3/C9. Question arrival never triggers a partial Contexto
or Shino call; unprocessed sessions are indexed directly and remain available through the tail
channel.

## Memory construction

Every sanitized session is archived without a model call. Each complete B-session window invokes
Mr. Contexto once. Contexto emits typed semantic operations; deterministic validation resolves
paths, checks provenance, rejects unsafe writes, and applies accepted operations atomically.

The general Contexto instructions preserve:

- atomic quantities, dates, durations, and temporal operands;
- separate departure, journey, arrival, and return events;
- current and superseded values;
- provenance for independently useful facts.

After each batch, a deterministic coverage audit labels every high-priority user signal as
`graph_covered`, `duplicate`, or `session_index_fallback`. Coverage reports do not alter graph
revision hashes. A missing graph fact is therefore observable and still retrievable from raw
memory without a repair LLM call.

At every complete C-session boundary, Mr. Shino summarizes the graph state associated with those
session IDs. It remains a secondary memory view rather than a replacement for raw evidence.

## Lossless retrieval

At question time, deterministic BM25 searches five independent channels:

- complete role-tagged sessions, including assistant turns;
- graph memory cells and provenance;
- Shino summaries;
- uncovered Contexto signals;
- the unprocessed B-session tail.

The index uses Unicode tokenization, snake-case splitting, stable tie-breaking, `k1=1.2`, and
`b=0.75`. Graph paths, provenance excerpts, and summaries expand retrieval keys but never replace
the original session text. Temporal matches boost scores without filtering away the lexical
fallback.

Reciprocal channel selection produces bounded candidates: at most 12 sessions, 12 graph cells, four
summaries, and four coverage fallbacks.

## Dedicated Reader

The Reader receives the bounded retrieval package and returns a strict structured plan:

- `supportStatus`: sufficient, conflicted, or insufficient;
- an answer mode such as direct, update, temporal comparison, or abstention;
- at most eight selected sessions and 12 graph pointers;
- evidence facts with source references;
- explicit older/newer conflict resolution.

Unknown session and graph references are removed deterministically. A plan with no valid evidence
is forced to `insufficient`. Selected turns are paired with adjacent turns so assistant answers and
their user questions remain intelligible.

Benchmark question-type labels never cross the Python-to-Node agent boundary. The harness retains
them only for stratified reporting; graph construction, retrieval, Reader prompts, and answer
prompts receive no category metadata.

Each retrieved session contributes at most six focused turns: enough for two independently ranked
conversation windows plus one immediate follow-up pair. Exact named constraints may be grounded
elsewhere in the same selected conversation because an answer turn can depend on entity or
location context established earlier in that session. An unselected session can never satisfy the
guard.

Deterministic code never reverses an explicit Reader insufficiency decision merely because
retrieved text contains numbers. Quantitative and temporal operands remain available to the
Reader, but lexical heuristics cannot synthesize a supported evidence plan.

## Compact final answer

The final answerer sees only:

- the Reader plan;
- selected raw source turns, with selected turns before adjacent context;
- selected graph cells and provenance;
- selected summaries and resolved conflicts.

It does not receive the complete graph, full diff ledger, all summaries, or arbitrary recent
sessions. Evidence items are budgeted atomically; JSON is never truncated mid-item.

The mapper removes unknown and duplicate citations, distinguishes those two conditions in
diagnostics, rejects question-restatement answers, and refuses a supported result without valid
evidence. There is no hidden retry.

## Reliability and artifacts

OpenAI calls share provider/model pacing across Contexto, Shino, Reader, and Answer while retaining
role-specific semaphores. Valid structured responses are persisted before deterministic
application. Resume accepts a cached response only when its prompt, schema, provider, model,
parameters, and input hashes match.

Each case adds:

```text
contexto-coverage/
retrieval/index-manifest.json
retrieval/candidates.json
reader-plan.json
final-context.json
```

The existing event stream, graph mutations, summaries, model calls, final graph, answer, and replay
hashes remain intact. Pre-0003.2 case artifacts cannot be resumed under the new artifact schema.

## Memory Observatory

The read-only inspector presents the complete diagnostic funnel:

```text
Contexto coverage → retrieval channels → Reader selection → compact answer evidence
```

It exposes coverage fallbacks, ranked candidates, Reader facts and conflicts, compact final
context, and per-role calls, tokens, latency, retries, and failures. These observer features make
zero additional model calls and remain safe for legacy runs with no 0003.2 artifacts.

## Validation discipline

The repair is validated through immutable sequential gates: baseline freeze, shared limiter,
Contexto coverage, deterministic retrieval, Reader, final answer, exposed end-to-end regression,
and a sealed untouched 18-case proof. A gate must meet its quantitative thresholds before the next
behavioral change begins. Cases used for development cannot later be claimed as blind validation.
